- 解释器：项目 `.venv-yolo/Scripts/python.exe`
- 工作目录：项目根目录

- 默认性能配置 `--tracking-profile threads`：640像素宽/350点不变，仅OpenCV改为4线程，并将检测框/置信度/类别合并为一次CPU回传。`--tracking-profile reference`恢复本机旧32线程；`--tracking-profile fast`为实验性480像素/200点/4线程，不自动作为已验收配置，需完整视频检查。检测输入仍1280、FP16、阈值0.05、原权重不变；没有降低外观提取频率。

- 外观模型默认 `weights/yolo26n-cls.pt`（预训练分类骨干，不是敌我分类器，也不是游戏专门训练的 ReID）。首次正式运行会由 Ultralytics 下载；联网失败会明确报错，不会偷偷关掉外观匹配。可用 `--appearance-model C:/路径/yolo26n-cls.pt` 指定已下载文件。其输入为人物裁剪，224×224，批量 CUDA FP16 特征提取；极小框（宽<10或高<20像素）无可靠特征，只保留位置关联。
- V4 默认显示当前已确认框，以及无公开编号的灰色“待确认/未关联”当前检测框；不会把真实检出因为尚未关联而完全隐藏。灰框不代表身份已确认，不能用来证明允许攻击。预测虚线仍默认不画，预测保留日志；需要时加 `--show-predictions`。baseline保持旧版待确认框隐藏行为。
- 默认只输出跟踪画面，1920×1080。需要原始检测与跟踪左右对照时加 `--split-view`，输出3840×1080。
- 更换片段：`--episodes 6 9 33`。更换录像目录：`--source D:/FPS_AI_Dataset/Apex_YOLO_DAY2_VAL`。
- 仅检查输入：`--check-only`。
- 位置预测默认 `--max-lost 0.2` 秒，独立轨迹缓存默认 `--memory 0.8` 秒。记忆保留不代表仍知道准确位置。
- 默认采用 NVIDIA `h264_nvenc` 硬件编码，无需参数；需要 CPU 编码时显式设置 `--encoder libx264`。YOLO 在 CUDA 上推理，解码、PIL 绘框与像素转换仍使用 CPU，不承诺整条链路都在 GPU 上。

## 流程与输出

视频解码 → YOLO 单帧检测 → 人物裁剪外观特征提取 → 背景光流估计镜头变化 → 旧轨迹重投影到当前画面 → 外观/位置门控 → 全局一对一关联 → 原有身份确认/短时记忆 → 画框 → 输出 MP4。

结果在 `runs/c1_tracking/时间戳/episode_编号/`：

- `跟随演示.mp4`：默认1920×1080，仅跟踪；`--split-view` 时左侧原始检测，右侧跟踪。
- `tracks.jsonl`：每个编码帧的原生时间戳、原始检测、轨迹状态和编号；`association_diagnostics` 包含镜头估计状态、内点数/比例/变换矩阵，以及匹配的检测索引、分数和外观相似度。不保存高维特征，也不把预测当成真实检测。
- `summary.json`：诊断计数和同步 predict() 耗时，不是端到端实时延迟。
- 两张预览 JPEG。

视频播放速度沿用原录像编码 FPS；跟踪时钟使用原生呈现时间，不以帧号/FPS 推算。相同源时间戳重复帧不重复积累确认次数。没有读取/对齐控制器数据。

## 原理与边界

### 镜头补偿

`c1_tracking_advanced.py:CameraCompensator` 将画面缩小到640像素宽，在背景找角点；掩蔽人物框、常见HUD、准星和持枪区域；前后向光流一致性筛选后，以RANSAC拟合局部仿射（平移、旋转、等比例缩放）。合格变换把旧框和人物自身速度转换到当前画面坐标，不把镜头平移写成人物持续速度。`last_observed_box` 保留最后真实检出的原始框；内部补偿框不冒充历史真实框。

低纹理、模糊、快速转动、视差、枪口闪光可能让估计失败。失败明确记为 `camera_rejected`；相邻原生时间间隔>100ms记为 `camera_timestamp_gap`。新版不因亮度突变清空轨迹；没有证明实际切镜，不强制重置。真正场景切换或长时间离开仍不保证身份连续。

### 外观与全局关联

`AppearanceEncoder` 把预训练模型的嵌入特征归一化，每条轨迹最多保留5个近期实际检出特征。外观余弦相似度与补偿后的IoU、中心距离、面积比共同评分；强外观不一致禁止继承编号。不是以“敌人/队友”类别作为硬关联条件，也没有读取头顶文字。

`global_assignment` 使用带未匹配虚拟列的匈牙利算法。V4 分组关联：近期已确认轨迹 → 强证据记忆轨迹 → 未确认轨迹；每组均做全局一对一分配。未确认杂轨迹不再参与第一组歧义投票。候选分数近似（差<0.04）时拒绝继承身份，但不重新求解并强接第二名。

拒绝关联不等于立刻出现新人。有旧轨迹可解释、或就在近期已确认旧框附近但外观暂时冲突的检测，暂缓新建轨迹。当前检出继续灰框显示，无公开编号、`state=unassociated`、`track_id=null`、`association_valid=false`、`class_id=null`、`position_valid=true`（位置来自当前真实检测，身份不成立）。未确认轨迹当前框也显示灰框但不展示临时内部编号。只有无法由现有轨迹合理解释的检测才建立新临时轨迹，再累计三次确认；始终不凭空补检测。

代价是近距离身份歧义可能暂时没有公开编号，而不是强行串号或新旧编号刷屏。这些阈值是初始启发式，不是校准后的同人概率，必须在原视频验收。相同皮肤、模糊和遮挡可使通用分类骨干外观不够区分，不能承诺永久编号或真实身份正确。

连续三次观测确认轨迹。身份档案保存最近400ms的观测，按原生时间指数衰减（120ms尺度）计算置信度加权证据。当前类别冲突立即显示“不确定”；至少连续三次相反判断且近期证据占比达到75%才更改历史身份。短暂冲突后至少两次原类别且证据占比达标才恢复。持续误分类仍可能形成稳定但错误身份，这不是ID文字识别。本轮不改动这套敌我证据规则，不训练识别模型。

短时漏检按屏幕坐标匀速外推，最多0.2秒。已确认轨迹的档案独立保存最多0.8秒；未确认轨迹仍在0.2秒后过期，避免长期保留杂框。超过预测期但未超过记忆期时，状态为 `remembered`、框为 `None`，只有历史位置，没有当前有效位置。顶部显示少量不可见目标的编号与最后检出距今时间，不重新画记忆框。

新版记忆重接需要更强外观证据（余弦相似度≥0.90）、合理位置距离和面积比，缺外观时不强接长期记忆。位置的0.2秒外推仍冻结，但镜头变换持续补偿缓存坐标；不连续外推人物运动0.8秒。成功重接后清空旧身份投票，至少三次新观测才允许恢复类别；恢复前显示不确定。缓存超过0.8秒或关联不可靠时，允许使用新编号。不能保证接回同一个人。

日志 `class_id` 表示当前可确认类别；`historical_class_id` 仅表示历史档案，不能当成当前敌人证据。`position_valid` 只对当前检测为真，预测或记忆均为假；`association_valid` 还要求轨迹已确认且当前检出。`summary.json` 包含 `tracker_version=4`、模式、外观模型路径、镜头补偿接受/拒绝、歧义关联、`birth_deferred`、`unassociated_detection_boxes`、`ever_confirmed_track_count`与原有计数。`created` 含未确认临时轨迹，不能当成人数或公开换号次数。`run_config.json` 保存检测/外观权重路径与文件SHA256。统计量不是准确率。

每帧增加 `events`（重复源时间戳帧不重复计事件）；关联诊断包含 `pair_gate_counts`（位置/面积/外观/记忆门限拒绝次数）、`deferred_births`（暂缓编号的检测索引与原因）、`expired_tracks`（过期ID与真实缺失时间）和生命周期各组数量。类别冲突期间冻结外观库写入，避免把明显冲突的裁剪继续写进历史档案；这不能证明其余匹配无误。

这是自定义时间戳原生跟踪器，不直接调用按帧推进的BoT-SORT；采用其常见的镜头/外观辅助关联思路，但不是完整BoT-SORT或卡尔曼实现。仍是屏幕坐标近似，不是反后坐力、自动瞄准或世界坐标推断。没有视频跟踪真值，因此计数不能证明跟踪准确率。

### 耗时解释

`phase_timings_ms.appearance` 为批量裁剪/外观网络/特征CPU回传耗时；`tracking` 含CPU光流、RANSAC、全局分配和状态更新。`detection_and_tracking` 现在包含检测＋外观＋跟踪，分别报告中位数/p95。模型首次下载/初始化/预热不计入稳态帧耗时。绘框/解码/编码仍单列；没有实测前不声称维持旧延迟或实时60FPS。各阶段p95不能直接相加。

新增细分：`camera` 镜头补偿总时间，`association_and_state` 重投影/匹配/状态更新；`camera_prepare` 缩放灰度掩码、`camera_corners` 角点、`camera_flow_forward/backward` 前后向光流、`camera_filter` 一致性及向量化掩码筛选、`camera_ransac` 仿射估计。子阶段未执行时记0，细分和外层tracking存在少量诊断/记录开销差别，不是新的独立总延迟。每帧摄像估计日志也包含 `timings_ms`。视频summary及run_config记录性能配置。

## CPU配置对照测速（用户在PyCharm运行）

1. 入口 `benchmark_c1_camera_profiles.py`，解释器 `.venv-yolo/Scripts/python.exe`，工作目录项目根目录，参数留空。
2. 默认找到最近完成的035跟踪日志，复用相同原始检测，分别重放整段视频测试 reference/threads/fast。只测CPU镜头补偿，无YOLO/外观推理、绘框、编码、训练、控制器输出或服务启动。每个配置独立顺序重放，使用同样RANSAC随机种子；不会改默认配置或覆盖旧结果。
3. 前30个唯一时间戳帧仅从稳态耗时排除，质量状态计数仍包含全部。单独报告后2/3的耗时，边界按原生时间计算，边界处不清空历史。重复源时间戳不重复更新。解码不计入CPU镜头补偿耗时。
4. 输出 `runs/c1_camera_benchmark/时间戳/测速报告.md` 与 `summary.json`。状态差异和共同接受矩阵的屏幕位移差仅表示与参考算法的一致性，不是准确率，不自动以“拒绝少”选优。CPU测试与YOLO共享负载的真实demo条件不同，所以后续仍需完整检测+跟踪测速。
5. 先在现用脚本以 `--episodes 35 --tracking-profile threads` 检查画面及整体耗时；实验性fast只在CPU测速结果值得尝试且用户决定进一步验收时启用。随时用reference回退性能参数，不删除既有结果。

## 本轮人工观察

先检查：同一个人编号是否持续；两个靠近的人是否串号；敌我是否先转不确定而非立即认反；遮挡时是否显示顶部记忆状态；重新出现时是否谨慎重接；超过记忆期是否及时清除。黄色预测框只在显式开启时观察。

反馈给出片段编号与视频秒数。先看完整流程，再针对失效场景决定补录或调整，暂不追加训练。
